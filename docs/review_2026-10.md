Я прочитал весь код, JSON-онтологию, интерфейс, эксперименты и текущую базу индексов, а также прогнал несколько read-only проверок на этой машине. Ничего в проекте не менял; временные скрипты лежали вне репозитория.
1. Главный вывод
Прототип живой: индексация, CLAP-поиск, Gradio-интерфейс, обогащение через Demucs + Whisper, объяснения и ASR-эксперимент реально работают. Но заявленные «четыре канала» пока не равноправны:
- по-настоящему работают CLAP-поиск по описанию и точное совпадение по метаданным;
- лирический канал фактически не подключён к поиску;
- метаданные ломаются на простом запросе lonely day;
- правила содержат несколько логических ошибок;
- CLAP-индексация недетерминирована: один и тот же трек при повторном прогоне получает разные жанры и настроения.
Поэтому до защиты нужно не «добавить ещё моделей», а починить корректность каналов, детерминизм, слияние оценок, тесты и экспериментальную часть.
2. Что реально умеет приложение сейчас
2.1. Индексация
Реализованы два прохода.
Лёгкая индексация (soundseek_core/indexer.py:223-288):
- берётся 30-секундный фрагмент из середины трека;
- CLAP считает 512-мерный аудиоэмбеддинг;
- читаются теги и обложка через mutagen;
- определяется content_type (music / speech / singing / animal / nature / sound_effect / noise / silence);
- для music выполняется flat zero-shot по 32 промптам поджанров;
- отдельно определяется настроение;
- трек сохраняется в FAISS-индекс аудио и в pickle-базу.
Приоритет жанра действительно реализован: тег → имя файла → CLAP (indexer.py:167-181).
Тяжёлое обогащение (indexer.py:315-340):
- Demucs отделяет вокал во временную папку;
- Whisper base транскрибирует;
- если текст длиннее 15 символов, MiniLM считает 384-мерный эмбеддинг и обновляет текстовый FAISS;
- база сохраняется после каждого трека.
В UI есть очередь: кнопка «Распознать текст», статусы idle → queued → running → done/error/has_lyrics, фоновый поток (web_app/app.py:38-120).
2.2. Поиск
Searcher.search (soundseek_core/searcher.py:35-83) делает следующее:
1. ищет полное вхождение всего запроса в title + artist + album + id;
2. считает CLAP-эмбеддинг текста и ищет по аудиоиндексу;
3. объединяет кандидатов и дедуплицирует по id;
4. применяет 5 правил;
5. формирует объяснения.
Поиск по аудиофрагменту (searcher.py:85-126) считает CLAP-эмбеддинг аудио и ищет по тому же FAISS-индексу.
2.3. Символьный слой
- Онтология: 52 жанра, 29 настроений, 8 типов контента, 80 групп ключевых слов, иерархии и related_moods / related_genres (soundseek_core/knowledge/ontology.json).
- 5 правил: genre_match, mood_match, metadata_match, lyrics_match, genre_conflict (soundseek_core/rules.py:101-107).
- Объяснения действительно строятся из сработавших правил, а не являются заглушкой.
Это уже соответствует формальному требованию гибридности, но символьный слой пока тонкий: он в основном переранжирует, а не фильтрует и не валидирует нейросетевые гипотезы.
2.4. Интерфейс
Три вкладки:
- поиск по тексту;
- поиск по напеванию/аудиофрагменту;
- библиотека: добавление файлов, переиндексация, таблица треков, кнопка распознавания текста, плеер, обложка, редактирование тегов, жанра, настроения, текста и личных заметок.
Интерфейс рабочий, но у него есть проблемы производительности и UX (ниже).
2.5. Эксперименты
ASR-эксперимент реально проведён: 2 трека × 2 условия (mix/vocals) × 2 модели (base/small), WER/CER/время. Результаты лежат в experiments/results/results.json.
Уточнение по выводам:
- для английского Demucs действительно даёт −28,6 % WER для base и −47,3 % для small;
- для русского на base WER даже немного вырос: 0,5300 → 0,5438;
- для русского на small улучшение есть: 0,4147 → 0,3641;
- small точнее, но на этих двух треках медленнее не «в 2–3 раза», а в 1,8–6 раз.

4. Критические проблемы и как их чинить
P0-1. CLAP-индексация недетерминирована
Симптом. Один и тот же трек при повторной индексации получает разные жанры и настроения.
Причина. У ClapFeatureExtractor для laion/clap-htsat-unfused стоит:
- max_length_s = 10;
- truncation = "rand_trunc".
Вы подаёте 30 секунд, а процессор случайно выбирает 10-секундный кусок. Я прогнал один и тот же 30-секундный фрагмент lonely_day пять раз и получил:
- progressive_rock / happy;
- hard_rock / rebellious;
- hard_rock / playful;
- hard_rock / happy;
- indie_rock / happy.
Косинус между эмбеддингами 0,95–0,99, то есть вектор почти тот же, но аргмакс по промптам перескакивает. Именно поэтому в базе у lonely_day стоит playful, а при новом прогоне получается rebellious.
Как чинить.
- Не полагаться на rand_trunc.
- Самый простой вариант: детерминированно брать фиксированные 10 секунд из середины и явно отключать случайную обрезку.
- Более качественный вариант: считать эмбеддинги для 3 фиксированных 10-секундных фрагментов (начало, середина, конец) и усреднять их. Стоимость вырастет примерно в 3 раза, но это всё равно доли секунды на трек.
- Либо использовать truncation="fusion" и передавать is_longer, если нужен именно длинный контекст.
- После изменения обязательно переиндексировать библиотеку.
- В базу добавить embedding_version и параметры нарезки, чтобы старые и новые эмбеддинги не смешивались.
P0-2. Поиск по метаданным ломается на lonely day
Симптом. Запрос lonely day не находит трек lonely_day. В top-3 оказываются Ms. Miku After Dark, Obywatel G.C. и Take On Miku.
Причина. В _exact_metadata_match (searcher.py:16-26) ищется вся строка целиком:
haystack = f"{t.title} {t.artist} {t.album} {track.id}".lower()
if q in haystack:
В id и title стоит lonely_day с подчёркиванием, а запрос — lonely day с пробелом. Полное вхождение не срабатывает. CLAP-канал тоже не спасает: трек не попадает даже в top-10 кандидатов, поэтому правило metadata_match до него не дотягивается.
Как чинить.
- Сделать отдельный лексический канал по метаданным, который работает по всем трекам, а не только по кандидатам CLAP.
- Нормализовать текст: нижний регистр, ё → е, _, -, ., /, \ заменить на пробелы, убрать пунктуацию.
- Токенизировать и считать совпадения по полям с весами: title > artist > album > id > path.
- Давать бонус за точную фразу и за совпадение всех токенов.
- Добавить нечёткое совпадение (например, rapidfuzz) для опечаток.
- Исключить из метаданных полный путь: сейчас запрос soundseek поднимает все треки, потому что у всех в пути есть SoundSeek.
После этого lonely day должен находиться по токенам lonely + day.
P0-3. Лирический канал фактически не подключён
Симптом. Поиск по строкам из песни работает только случайно.
Причина. Searcher.search вызывает только:
- _exact_metadata_match;
- _semantic_search через CLAP.
VectorDB.search_text (soundseek_core/db.py:67-68) нигде не используется, кроме устаревших check_scripts. То есть 384-мерный текстовый FAISS существует, но поиск по нему не идёт.
Строки ищутся только внутри rules._boost_on_lyrics, то есть только у тех треков, которые уже попали в кандидаты CLAP. Если CLAP не вернул трек, его текст никогда не будет проверен.
Дополнительно:
- all-MiniLM-L6-v2 — английская модель, а тексты и запросы у вас частично русские;
- для треков без текста в индекс добавляется нулевой вектор, и search_text может возвращать их с score 0;
- в базе только 5 текстов, из них 3 музыкальных.
Я вручную дернул текстовый индекс:
- запрос most lonely day of my life даёт lonely_day с 0.655;
- запрос they're eating my flesh даёт нужный трек с 0.942;
- запрос should be banned даёт lonely_day только 0.085, потому что Whisper распознал не «should be banned», а «should it expired».
Как чинить.
- Подключить текстовый канал в Searcher: лексический поиск по строкам + db.search_text.
- Фильтровать None и нулевые векторы.
- Использовать мультиязычную модель (paraphrase-multilingual-MiniLM-L12-v2 или intfloat/multilingual-e5-small, обе 384-мерные) и переэмбеддить тексты.
- Объединять каналы через RRF или нормализованные оценки, а не через абсолютные прибавки.
- Хранить не только полный текст, но и сегменты Whisper с таймкодами — тогда в объяснении можно показать конкретную строку и время.
- Для коротких клипов и инструменталов не запускать распознавание вообще.
P0-4. Ошибки в правилах и разборе запроса
Это, пожалуй, самая опасная часть для демонстрации.
4.1. Правила используют сырой тег вместо нормализованного жанра
В rules.py:110-128 и 226-238 берётся:
genre = track.tags.genre or track.derived.genre
У трека 02 - Театральный демон тег Punk;Rock, а derived.genre = punk_rock. Сравнение is_genre_related('punk_rock', 'Punk;Rock') даёт False. В результате трек получает:
- +0.20 за настроение happy;
- −0.20 за «жанр не соответствует запросу».
Итог: в запросе весёлый панк единственный настоящий панк-трек проигрывает Grzyby Na Marsie с жанром rap.
Как чинить. В правилах всегда использовать нормализованный derived.genre, а сырой тег хранить только как источник/провенанс. Либо при редактировании тега сразу пересчитывать derived.genre через онтологию.
4.2. Подстрочное распознавание жанров
Ontology.extract_concepts (ontology.py:52-67) ищет ключевые слова как подстроки. Поэтому:
- trap → rap + trap;
- synthpop → pop + synthpop;
- k-pop → pop + k_pop;
- pop punk → pop + punk_rock + pop_punk.
Дальше genre_conflict берёт только concepts["genres"][0], а список строится из set, то есть порядок зависит от хеш-рандомизации Python. Поведение может меняться между запусками.
Как чинить. Сортировать ключевые слова по длине, искать по границам слов, сначала匹配 самые длинные фразы, а короткие игнорировать, если они уже покрыты. Возвращать не список из set, а детерминированно упорядоченный список.
4.3. Одновременное срабатывание взаимоисключающих правил
На запросе рок, но не панк для SOAD Cigaro я получил одновременно:
- genre_match +0.30 — потому что heavy_metal является потомком rock;
- genre_conflict −0.20 — потому что первым жанром из запроса оказался punk_rock.
То есть правила сами себе противоречат.
Как чинить. Хранить структурированный запрос:
genres: list[str]
negated_genres: list[str]
moods: list[str]
negated_moods: list[str]
has_vocal: bool | None
genre_conflict должен срабатывать только если ни один положительный жанр не связан с треком. Отрицательные жанры должны быть жёстким фильтром или сильным штрафом с отдельным объяснением.
4.4. Отрицания не поддерживаются
рок, но не панк всё равно извлекает punk_rock. весёлое, но без вокала не извлекает вообще ничего: в keywords есть весёлый, веселая, весёлая, но нет весёлое; без вокала не обрабатывается.
Как чинить. Новый query_parser.py, который:
- нормализует ё → е, регистр, пунктуацию;
- использует pymorphy3 или простой стеммер для русской морфологии;
- ищет отрицания в окне перед/после концепта: не, без, кроме, not, without;
- поддерживает has_vocal, год, исполнителя, диапазон лет;
- выдаёт английский семантический запрос для CLAP.
4.5. Пропущенные ключевые слова
Не распознаются:
- тяжёлый метал, метал, metal;
- весёлое;
- альтернатива в некоторых формах;
- instrumental, без вокала.
Как чинить. Дополнить словарь и добавить нормализацию/лемматизацию, а не полагаться на точные словоформы.
P0-5. Шум в метаданных и отсутствие нормального слияния оценок
Правило metadata_match (rules.py:158-186) включает в meta_text полный track.path и не имеет стоп-листа для типовых слов. Поэтому:
- ambient calm music даёт +0.35 треку Монеточка - Нет монет (Official Music Video) за слово music;
- запрос soundseek поднимает все треки;
- один общий токен может перевесить сильный CLAP-результат.
Плюс нет нормализации оценок:
- exact metadata = 1.0;
- CLAP ≈ 0.1–0.6;
- правила добавляют абсолютные 0.2–0.5.
В итоге final_score бывает 1.6 и 0.005. Нет порога «ничего не найдено»: на любой запрос вернётся 5 результатов.
Как чинить.
- Убрать path из метаданных или дать ему минимальный вес.
- Добавить стоп-лист: music, song, audio, official, video, lyrics, feat, ft, трек, песня, музыка, клип, официальный.
- Взвешивать поля: title > artist > album > id > path.
- Требовать либо фразу, либо 2+ совпавших токена для сильного бонуса.
- Использовать RRF ( Reciprocal Rank Fusion ) для объединения каналов и небольшие rule-бусты сверху.
- Ввести порог и состояние «ничего не найдено».
- Ограничить итоговый score диапазоном 0, 1 или показывать не «сырой» score, а процентиль/ранг.
P0-6. Гонки потоков и целостность базы
_worker_loop (web_app/app.py:48-71) пишет в indexer.db и вызывает db.save. В это же время UI может:
- добавить файлы и запустить index_folder_light;
- нажать force reindex и сделать reset_db;
- выполнить поиск.
_worker["lock"] защищает только очередь, но не базу. db.save пишет три файла напрямую, без временного файла и os.replace. При совпадении операций можно получить потерянные треки или рассогласование FAISS-индекса и списка tracks.
Дополнительно:
- done/error живут только в памяти;
- после перезапуска инструментальные треки снова idle;
- enrich_with_lyrics выбирает все треки без текста и будет снова и снова пытаться обработать инструменталы;
- после done или error кнопка заблокирована, повторить нельзя.
Как чинить.
- Один threading.RLock на все мутации базы и сохранение.
- Атомарное сохранение: писать в .tmp, затем os.replace для всех трёх файлов; добавить manifest с версией, количеством треков и размерностями.
- При force reindex останавливать воркер и дожидаться его завершения, а не просто чистить очередь.
- Хранить в Track статус обогащения (idle/queued/running/done/error/skipped), ошибку и время попытки.
- Разрешить повторный запуск после error и done.
- Добавить DB_VERSION и миграцию старых pickle-файлов.
P0-7. Жизненный цикл библиотеки
Сейчас:
- id = Path(path).stem — два файла с одинаковым именем в разных папках конфликтуют;
- нет mtime/размера/хеша — заменённый файл не переиндексируется;
- удалённый файл остаётся в базе;
- обложки удалённых треков не чистятся;
- пути хранятся абсолютными (Path(path).resolve()), поэтому перенос проекта ломает воспроизведение.
Сейчас в базе 24 трека и на диске 24, но это совпадение, а не гарантия синхронизации.
Как чинить.
- Стабильный ID: хеш относительного пути (или относительный путь + размер + mtime).
- Хранить относительные пути от корня проекта.
- Добавить file_mtime, file_size, index_version.
- При сканировании сравнивать mtime/размер и переиндексировать изменённые; удалять отсутствующие.
- Для FAISS при удалении проще всего пересобрать индекс — для персональной библиотеки это нормально.
- Обложки хранить с тем же ID и удалять при удалении трека.
P0-8. content_type, singing и has_vocal
В classify_audio (indexer.py:148-155) при content_type != "music" стоит ранний return. Поэтому для singing не считаются ни жанр, ни настроение.
В текущей базе два полноценных трека — Всё ли понарошку и Колыбельная — имеют content_type=singing и пустые genre/mood.
has_vocal — обычный bool со значением по умолчанию False. Для необработанных треков UI пишет «нет», хотя правильно писать «неизвестно». Из-за этого запрос «без вокала» невозможно честно реализовать.
Как чинить.
- has_vocal: Optional[bool] = None: True — есть текст/вокал, False — проверено и вокала нет, None — не проверяли.
- Эвристика: если content_type == "singing" и длительность > 60 с → считать music и продолжать классификацию жанра/настроения.
- Аналогично для speech на длинных треках, если музыкальный score близок.
- Для коротких клипов (< 15–20 с) не запускать распознавание и не делать вывод об отсутствии вокала.
- В UI показывать «неизвестно», а не «нет».

5. Приоритетный план доработки
Этап 0. Стабилизация перед защитой (2–4 дня)
1. Детерминированная нарезка CLAP и переиндексация библиотеки.
2. Нормализация жанра в правилах; структурированный Query; детерминированный разбор.
3. Лексический канал метаданных по всем трекам + подключение текстового FAISS.
4. RRF/нормализация score + порог «ничего не найдено».
5. Блокировка БД, атомарное сохранение, статусы обогащения.
6. Тесты на найденные баги:
- lonely day находит lonely_day;
- весёлый панк не штрафует Punk;Rock;
- trap не превращается в rap;
- рок, но не панк не даёт одновременно +0.3 и −0.2;
- music в имени файла не даёт metadata-бонус;
- один и тот же аудиофрагмент 5 раз даёт одинаковый жанр.
Этап 1. Качество поиска (1–2 недели)
1. query_parser.py: отрицания, has_vocal, год, исполнитель, морфология, английское расширение запроса для CLAP.
2. Мультиязычная модель для lyrics (multilingual-e5-small или paraphrase-multilingual-MiniLM-L12-v2) + переэмбеддинг.
3. Лирический канал: лексика + эмбеддинги + сегменты с таймкодами.
4. Метаданные: веса полей, стоп-лист, fuzzy-совпадения.
5. Онтологическая валидация нейросетевых гипотез: если CLAP поставил жанр punk_rock, а настроение calm, а в онтологии у punk_rock related moods — energetic/aggressive/rebellious, снижать уверенность или помечать «требует проверки». Это сильный гибридный ход: символьный компонент начинает реально фильтровать нейросетевые гипотезы, а не только переранжировать результаты.
6. Кэширование эмбеддингов промптов: сейчас _best_prompt заново кодирует 8 + 32 + 29 текстов на каждый трек. Это можно считать один раз при загрузке онтологии и сильно ускорить классификацию (сейчас ~0,9 с из 1,2–1,8 с на трек).
Этап 2. Обогащение и UI (1 неделя)
1. Сначала читать встроенные тексты: ID3 USLT/SYLT, FLAC LYRICS, MP4 ©lyr, sidecar .lrc.
2. Если текста нет — Demucs + VAD + Whisper; лучше faster-whisper с int8 на CPU.
3. Сохранять язык, сегменты, среднюю уверенность, источник текста.
4. Кэшировать отделённый вокал по хешу файла, чтобы не гонять Demucs повторно.
5. Batch-обогащение только для music/singing длительностью > 20 с.
6. UI:
- не перерисовывать весь список каждые 2 секунды (сейчас gr.Timer + gr.render пересоздаёт все строки);
- добавить «ничего не найдено» и подсказки;
- показывать разобранный запрос: «понял: жанр=rock, настроение=sad, без вокала»;
- показывать источник и уверенность жанра/настроения;
- показывать сниппет текста с подсветкой совпадения;
- добавить клик по результату → карточка/плеер;
- экранировать HTML;
- добавить прогресс индексации и позицию в очереди;
- добавить удаление трека и повторное распознавание после ошибки.
Этап 3. Эксперименты для записки (1–2 недели)
1. Разметить 24–50 треков вручную: жанр, настроение, наличие вокала, язык, тип контента.
2. Составить 30–50 запросов с релевантными треками:
- метаданные;
- жанр/настроение;
- строки из песен;
- аудиоописания/фрагменты.
3. Сравнить 4 режима:
- только CLAP;
- только символьный (метаданные + онтология + правила);
- только текстовый/лирический;
- гибридный.
4. Метрики: Precision@5, Recall@10, MRR@10, NDCG@10; по категориям запросов и overall.
5. Абляции: без правил, без лирики, без метаданных, без английского расширения, с rand_trunc vs детерминированной нарезкой.
6. Отдельно оценить классификацию: macro F1 по жанрам/настроениям, confusion matrix, стабильность (5 прогонов одного трека).
7. ASR: расширить до 6–10 треков, base/small, mix/vocals, WER/CER/время/пиковая RAM.
8. Производительность: холодный/тёплый запуск, индексация, поиск, пиковый RSS.
9. Оформить таблицы, графики, error analysis.
Этап 4. Запланированные фичи (после обязательного)
1. UMAP/t-SNE по аудиоэмбеддингам. Для 24 точек UMAP будет нестабильным; лучше набрать 50–100 треков или использовать PCA/MDS как fallback. Plotly + цвет по жанру/настроению + клик → карточка.
2. Генератор плейлистов: извлечь tempo, RMS energy, spectral centroid, key; задать стартовое и конечное настроение; жадно/beam search выбирать 10 треков с плавным переходом; экспорт M3U.
3. Настоящий query-by-humming: librosa.pyin для мелодии, нормализация контура, DTW/chroma. Текущий CLAP-поиск фрагмента этого не заменяет.
4. Многосегментные эмбеддинги, аудиопризнаки для настроения, более музыкальная модель жанра — как исследовательские расширения.
6. Целевая схема после доработок
Запрос
  │
  ├─ QueryParser: RU → концепты, отрицания, фильтры, EN-запрос
  │
  ├─ Metadata lexical (по всем трекам)
  ├─ CLAP text → audio (FAISS)
  ├─ Lyrics lexical + multilingual MiniLM (FAISS)
  └─ Audio CLAP (если аудиозапрос)
        │
        ▼
  Candidate fusion (RRF)
        │
        ▼
  RuleEngine: жёсткие фильтры + бусты + онтологическая валидация
        │
        ▼
  Top-K + explanation trace + confidence/source
База должна хранить:
- стабильный ID;
- относительный путь, mtime, размер;
- content_type, genre, genre_source, genre_confidence;
- mood, mood_confidence;
- has_vocal: bool | None;
- lyrics, lyrics_source, lyrics_lang, lyrics_segments;
- user_notes;
- index_version.
